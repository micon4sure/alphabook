# Alphabook Format 1.0

Alphabook defines a minimal, human-readable and machine-readable format for
project planning in Git. Tasks, decisions, documentation and artifacts share
one planning branch, separate from code. Git, UTF-8 files and this specification
are sufficient; the web app and MCP interface are optional.

## Storage and discovery

The local `refs/heads/alphabook` branch holds planning files directly at its root,
with no dot-directory and no application code. It has independent history, not
a code branch with files deleted. Never merge planning history into code history.
No planning checkout is required. Read objects with `git show`/`git ls-tree`.
An optional checkout is just another way to edit the same files, not required
infrastructure. The reference tools use an isolated index inside the common Git
directory for writes; they never switch code HEAD or use its index.

```text
alphabook branch
  project.yaml
  tasks/T-001.md
  decisions/D-001.md
  docs/
  artifacts/
```

`project.yaml`:

```yaml
format: alphabook
format_version: "1.0"
id: "b27d509e-e6a1-4dd4-a665-39966ce304c0"
name: Alphabook
planning_branch: alphabook
code_branch: main
```

The UUID is stable across clones and worktrees; an independent fork may choose
a new UUID. `planning_branch` is exactly `alphabook`. Optional
`code_branch` describes the project's preferred code integration branch; its name
is not prescribed. It does not select a planning snapshot. Local registrations
also identify the Git common directory so separate clones are not conflated.

Readers must reject unsupported versions, not infer a format from a folder name.
The application does not import planning files from code checkouts. Only
`project.yaml` and the four directories above are allowed in the planning tree.
Readers validate the selected current tree, require one root,
and reject history shared with the preferred code branch when it is available.
After cloning, an ordinary local `alphabook` branch may need to be created from its
remote-tracking branch. Reading a local ref does not imply it has been fetched.
One root project manifest per Git repository is specified; monorepo subdivisions
and cross-repository dependency graphs remain future work.

## Files, metadata and references

Task and decision files use YAML frontmatter delimited by exact `---` lines,
followed by Markdown. UTF-8 without BOM, LF or CRLF. The filename stem must match
the case-sensitive ID. IDs are unique across tasks and decisions. UUID-based IDs
avoid allocation collisions; short IDs require coordination.

Metadata uses YAML 1.2 core scalars restricted to JSON values. Mapping keys must
be strings; duplicate keys, aliases, anchors, explicit tags and nonfinite numbers
are invalid. Dates are strings. Unknown core fields are invalid. Namespaced
`extensions` are permitted and must be preserved when other fields are edited.
The normative schema is `schemas/1.0/schema.json`.

```yaml
kind: task
id: T-001
title: Implement project registration
status: in_progress
depends_on: []
decisions: [D-001]
assignee: agent-1
branches: [task/T-001]
paths: [src/registry.ts]
artifacts: [artifacts/T-001-tests.md]
```

Task states: `planned`, `in_progress`, `blocked`, `review`, `done`, `cancelled`.
`review` means implementation is ready for review/integration; `done` means the
task's acceptance criteria have been met. Neither a commit nor a branch merge
silently changes status. Record a blocked reason in the body. The body should
describe the outcome, scope, acceptance criteria and verification evidence.

Dependencies must exist and form a DAG. A planned task is ready when all
dependencies are done in the shared plan. Cancelled/review tasks do not satisfy
dependencies. Invalid plans must not be advertised as ready to execute.

Optional `branches` contains short code branch names (not `alphabook` or machine
paths). Names must pass Git ref validation; absence locally is a visibility
warning, not a schema violation. Optional `commits` holds full lowercase 40- or
64-character code commit IDs. Unavailable objects must be reported as unavailable.
Do not store the hash of the planning commit containing that same field.

Decision states: `proposed`, `accepted`, `superseded`, `rejected`. Optional
`supersedes` references another decision and must be acyclic. Task `decisions`
references must exist. All reference validation uses a single alphabook snapshot.
Keep historical records where possible; cancellation is usually preferable to
deletion. Deletes must not leave dangling references.

`paths` are literal relative paths into the code repository. Artifact paths are
under `artifacts/` in the planning tree and must exist. Neither allows
absolute paths, URI schemes, backslashes, `.git`, empty or traversal segments.
No wildcard expansion is implied. Readers never follow escaping symlinks. The
reference reader rejects planning symlinks/submodules entirely. Large binary/LFS
artifacts may require a separate viewer or payload retrieval; a pointer file must
not be presented as the actual artifact. Credentials and machine-local paths do
not belong in portable records.

## Code links and worktrees

Code commits use ordinary trailers:

```text
Implement registration

Task: T-001
```

Keys are case-insensitive, IDs are case-sensitive, and each trailer contains one
ID. Use Git's `interpret-trailers --parse` semantics, not arbitrary body matching.
Many commits can reference one task and one commit can reference many tasks.
Planning commits can use the same trailers, but must be distinguished from code
commits. Preserve task trailers when squashing. Rewrites can change commit IDs;
update explicit links as needed rather than claiming that stale IDs still resolve.

All code branches/worktrees refer to this one plan. A worktree's name/HEAD/dirty
state comes from Git; its tasks come from the central records' branch links.
There is no task database copied into each source checkout. A task/assignee is
recorded intent, not proof of a running process or an exclusive claim. Shared
worktrees share Git refs; independent clones only see exchanged Git history.

## Writes and concurrency

Every reference-tool mutation requires the expected `alphabook` commit ID and the
expected SHA-256 of exact file bytes (`null` means create a previously absent
file). A write validates the candidate complete plan, makes a planning commit,
then publishes with `git update-ref refs/heads/alphabook NEW EXPECTED`.

This compare-and-swap is the serialization point. If another writer advanced the
branch, reject the stale write. Re-read and reconcile; never blindly force push or
retry a replacement against a newer record without checking its content. Failed
attempts can leave unreachable Git objects, but must not advance the ref or change
code files/index. Git garbage collection handles unreachable objects normally.

The reference UI, CLI and MCP share this writer. Create, update and delete each
produce one real commit; there is no separate save-only state or database.
Direct branch writers refuse when `alphabook` is checked out, to avoid making its
working files/index stale. Ordinary editors can instead work in that checkout
and commit normally. Do not mix these modes concurrently. Raw Git commands remain
possible, but their caller must perform validation and concurrency checks.

Code and planning commits are deliberately separate. A completed implementation
should record its code commit and evidence in a following planning commit.
No transaction spans both histories; incomplete updates must be reported honestly.
Git exchange remains explicit. Sync both the relevant code branches and `alphabook`;
MCP is not required and GitHub is only an optional remote.

See `AGENT_PRIMER.md` for Git-only CRUD and `spec/mcp.md` for the convenience API.
