# Repository Project Format — experimental draft 0.1

Working name: RPF. Date: 2026-09-24. This describes a repository file format and
its semantics. It does not define an agent execution protocol. The words MUST,
SHOULD and MAY state requirements, recommendations and optional behavior for this
draft. No compatibility promise is made between different experimental versions.

The entire system MUST remain usable through files and ordinary Git without MCP,
Command Center, a daemon, a database or a claim/coordination service. MCP is an
optional planning interface that can edit `.command` records and commit those
edits. The web application may edit these same files directly; it does not need
an MCP connection in order to display or maintain a project.

## 1. Discovery and identity

A project root contains `.command/project.yaml`:

```yaml
format: repo-project
format_version: "0.1"
id: "b27d509e-e6a1-4dd4-a665-39966ce304c0"
name: Command
integration_branch: main
```

`id` is a persistent project UUID. Clones and worktrees preserve it. A deliberately
independent fork SHOULD choose a new UUID. Local registrations additionally
identify the checkout; a UUID alone cannot select a filesystem location.
`integration_branch` names the branch used for the accepted project plan. A local
application may map it to a fetched remote-tracking ref, but MUST identify which
ref/OID it read and whether its remote information is stale.

Readers MUST check the format/version before interpreting records. Another
`.command/` layout is not implicitly RPF. Unsupported versions can be displayed
as raw files but MUST NOT be rewritten as if their meaning were known.

Only one project manifest at a repository root is specified by 0.1. Monorepo
subprojects and cross-repository dependencies are future extensions.

## 2. Files and encoding

- `.command/tasks/<id>.md`: task metadata plus Markdown body.
- `.command/decisions/<id>.md`: decision metadata plus Markdown body.
- `.command/docs/`: ordinary documentation, with no required metadata.
- `.command/artifacts/`: optional evidence and other durable outputs.

Task/decision files begin with a line containing exactly `---`, a YAML mapping,
then another `---` line. Remaining bytes are the Markdown body. UTF-8 without a
BOM is required; readers accept LF or CRLF. The filename stem MUST match `id`.

Manifest/frontmatter use YAML 1.2 core scalar semantics restricted to JSON values:
string mapping keys, finite numbers, strings, booleans, null, arrays and objects.
Aliases, anchors, explicit tags, duplicate keys and nonfinite numbers are invalid.
Dates are ordinary strings. Writers SHOULD quote ambiguous values. Metadata is
validated using [JSON Schema 2020-12](https://json-schema.org/draft/2020-12) and
the bundled `schemas/0.1/schema.json`.

Record IDs are case-sensitive, stable, and unique across tasks and decisions in
one project. They are not derived from titles or branch names. UUID-based IDs are
recommended for concurrent creation; short IDs such as T-001 are allowed when
writers coordinate allocation. Readers MUST report duplicate IDs.

Paths are literal forward-slash paths relative to the project root; globs,
absolute paths, traversal segments, backslashes, `.git` components and URI schemes
are not allowed. Related code paths may describe files not created yet. Artifact
references MUST resolve to existing files inside the project. Readers MUST NOT
follow symlinks outside that root, including symlinks under `.command`.
Large artifacts MAY use ordinary Git LFS; an unavailable payload must be shown
as unavailable, not as a successful read of its pointer file.

Credentials, personal preferences, machine paths, logs/caches and live task claims
do not belong in these records. Namespaced `extensions` preserve optional data
without changing the core fields; readers may ignore their meaning and writers
MUST preserve them. Unknown core fields are invalid for this exact draft version.

## 3. Tasks and decisions

```yaml
kind: task
id: T-002
title: Add project registration
status: planned
depends_on: [T-001]
decisions: [D-001]
paths: [src/registry]
```

Task states: `planned`, `in_progress`, `blocked`, `done`, `cancelled`. Optional
`assignee` text identifies the current worker without implying an exclusive lock.
A Markdown
body SHOULD explain the intended outcome, acceptance and eventual evidence.
`blocked` describes an explicit impediment, with its reason in the body.
Dependencies are task IDs in the same project. They MUST exist and form an acyclic
graph. A task is dependency-ready when all its dependencies are `done` in the
selected snapshot. Cancellation does not satisfy a dependency. Status does not
silently change when files or commits appear.

Decision states: `proposed`, `accepted`, `superseded`, `rejected`. The body SHOULD
record context, decision and consequences. An optional `supersedes` field refers
to an existing decision; supersession links MUST be acyclic. Task `decisions`
references MUST exist, but do not imply a new approval or execution gate.
All references are validated within the SAME snapshot, never assembled by taking
one record from main and another from an agent's branch.

Tasks and decisions SHOULD be retained when finished so IDs remain meaningful in
Git history. Reopening/correcting a record is an ordinary explicit edit; the format
does not impose an immutable product workflow on users.

## 4. Git connection and snapshot semantics

The current checkout, including uncommitted file edits, is the working snapshot.
A committed snapshot is the complete tree at a specific Git OID. Interfaces MUST
identify project, checkout/branch or OID, and whether uncommitted changes are shown.
The accepted plan is the committed snapshot at `integration_branch`. An unborn
branch has no accepted snapshot yet; dirty integration-checkout edits are drafts.
The task graph is derived from records, never separately authoritative.

Use repeated, conventional commit trailers to associate work:

```text
Add project registration

Task: T-002
Task: T-003
```

Each `Task` trailer contains exactly one task ID; keys are case-insensitive and
values retain ID case. Parse the trailer block, not arbitrary subject/body text.
Git's [interpret-trailers](https://git-scm.com/docs/git-interpret-trailers) defines
the reference extraction behavior. One task can have many commits and one commit
can reference several tasks. Commits without trailers remain unassociated.

Implementation changes SHOULD commit source, record updates and evidence together.
Planning-only changes can be committed independently without changing source code.
Links are derived from commits reachable from the selected ref. Squash integrations
SHOULD retain the relevant task trailers. Rebases/reverts do not automatically
change task status; the resulting tree is authoritative. Historical links to a
record absent from today's tree remain historical links, not validation failures.
Do not record a commit's own hash inside that same commit's task file.

The format itself does not perform fetch, push, commits or merges. Tools may offer
explicit Git actions. No GitHub account or particular remote service is required.

## 5. Writers and interoperability

Editors, CLI tools, UI and MCP adapters operate on the same files. A database or
index MUST be reconstructable from project files and Git; it is not the only copy
of a task, decision or accepted update. Invalid intermediate/conflicted files MUST
be surfaced, not silently replaced by stale cached state.

Cooperating writers SHOULD use a per-checkout lock and compare an expected revision
(SHA-256 of exact current file bytes) before replacing a record atomically. A
missing file is distinct from an empty file. A mismatch reports a conflict and
does not overwrite. Writers preserve Markdown content and unknown extensions.
Multi-file operations need an explicit transaction strategy or must report partial
completion; 0.1 does not pretend ordinary file replacement is a distributed
transaction. Unsynchronized external editors can still race; tools must surface
detected changes and merge conflicts.

Conformance is split into a file reader, a file writer, and the optional worktree
view described in [worktrees.md](worktrees.md). Supporting the file format
does not imply task scheduling, exclusive claims or automated integration. An MCP mapping
is described separately in [mcp.md](mcp.md).

## 6. Deliberately open

The final name, wider status vocabularies, cross-repository work, remote claim
coordination and stable extension governance remain open. V0.1 is a small usable
experiment; additional requirements should follow real implementation experience.
